# 项目报告生成 Skill

用户需要以**项目**为单位汇报进展（给主管、给客户、给项目群），而不是以自己为单位。
这个 skill 的职责是：把指定项目在指定时间窗内的**全部提交**，翻译成一份能直接发出去的项目进展报告。

它和 `weekly-report` 是一对，差别只有两条，但这两条决定了整个流程：

| | weekly-report（个人周报） | 本 skill（项目报告） |
|---|---|---|
| 范围 | 扫描配置目录，自动发现所有有提交的仓库 | **只做用户给的路径**，隔壁项目提交再多也不写 |
| 提交 | 只统计用户本人（`--author` 过滤） | **统计全部成员的提交**，不加 `--author`——但报告里不出现是谁做的 |
| 时间 | 默认本周 | 默认本周（这一点相同） |

所以：用户问"我这周干了啥"→ 用 weekly-report；用户给一个项目路径问"这周进展到哪了"→ 用这个。
两个都沾边时（"写周报，顺便说说项目情况"）以用户的主诉求为准，不要两边都跑一遍。

## 配置

### 项目路径

**项目路径由用户在每次请求里给出**（通常长这样：`~/Documents/GitLab/Gmi`）。
不要主动去 `~/Documents/GitLab` 下遍历找项目，也不要维护项目清单——路径是唯一入口。

### 报告里的项目名

项目名用仓库目录名（如 `Gmi`）；路径指向一个装着多个仓库的目录时，就用那个目录名，
底下各仓库在口径里列清楚。
不需要给项目起业务名，也不需要维护"用户说法 → 路径"的对照表。

## 报告格式

固定三段式，每个项目一段。生成时严格遵循：

```
项目报告（<起> ~ <止>）

一、<项目名>
本周进展：
1. 【<子应用>】<工作项>
2. <工作项>
风险/问题：<无 / 一句话>
下周计划：<计划条目 / （暂无，待补充）>

二、<项目名>
本周进展：
1. ...
风险/问题：无
下周计划：...

口径：<分支（含最近 fetch 时间）/ 时间区间（写全时分秒）/ 提交数（不含 merge）/ 未逐条列出的零散提交数>
```

标题行写日期（`<起> ~ <止>`）便于扫读，口径里写全时分秒供核对，这个分工不要混。

**每个项目的三个字段一个都不能省**，即使内容为空也要保留字段名（写"无"或"（暂无，待补充）"）。
项目报告是给人扫一眼看状态的，字段缺位比写"无"更让人怀疑是不是漏了。
末尾的**口径**是报告的一部分，不是附赠说明——见第 7 步。

## 格式规则

- **项目**用中文数字编号：一、二、三
- **进展条目**用阿拉伯数字：1. 2. 3.
- **子应用前缀**只在项目是 monorepo 时加，形如 `【app-a】`；不是 monorepo 就直接写条目
- **每条工作项**一句话，不超过 30 字，保留 UI / API / URL / bug / token 等技术词
- **每个项目 3–10 条**（子应用多的 monorepo 最多 12 条）：超了说明同类项还没合并完，继续合并而不是继续罗列
- **时间口径跟着区间走**：默认写"本周进展"；统计的是上周/近两周时写"上周进展"/"近两周进展"
  （或者干脆写"进展"），别让字段名和首行口径打架
- **报告里不出现人名**：不写"谁做了什么"，也不列参与人名单——这份报告看的是项目本身，
  谁的提交都一样算数；真要写清分工，那是周报的事
- **风险/问题**没有就写"无"；**下周计划**没问到就写"（暂无，待补充）"，不要编

## 工作流程

### 第 1 步：确定项目路径

**用户会给项目文件夹路径**（这次请求里就直接给），所以不需要、也不要去 `~/Documents/GitLab` 下遍历找项目。
拿到路径后：

1. 先 `find <路径> -maxdepth 2 -name .git -type d` 看这个范围里有哪些仓库——
   路径本身是仓库（`<路径>/.git`）就用它；路径是个装着仓库的目录（比如某个分组目录下挂着 3 个仓库）
   就都用上
2. 目录下有多个仓库时，**默认整个目录一起统计**，并在报告开头说明范围（"按 xxx 目录下三个仓库统计"），
   让用户一眼能纠正——不用先停下来等确认，用户既然指了整个目录，多半就是要整个目录
3. 路径不存在、或者底下找不到任何 git 仓库 → **如实告诉用户**，别去别处找一个"最像的"顶上
4. 用户给了多个路径 → 就是多个项目，逐个统计

没给路径（少见，比如只说"写个项目报告"）→ 直接问"哪个目录？把路径贴给我"，
**不要自己去 `~/Documents/GitLab` 下扫一遍**：扫出来的清单再让用户挑，
等于让他做了一遍本该他一句话说清的事。

**只做给定路径里的项目。** 这是本 skill 与周报最大的行为差别：隔壁仓库这周再热闹也不写一个字。
用户后来说"再加 `<路径>`"再加。

### 第 2 步：确定时间范围

- 默认**本周**（周一到周日）；用户说"上周""近两周""这个月""9 月 1 号到 15 号"就按用户说的算
- "今天"用 `date +%Y-%m-%d` 拿，不要凭上下文猜；跨月跨年按真实日期算，不要按"本月的第几周"推
- **`--since` / `--until` 都必须带时分秒**：写 `--since="2026-09-14 00:00:00"`、`--until="2026-09-21 00:00:00"`，
  绝不能只写 `--since="2026-09-14"`。只给日期时，git 会把**当前时刻**补进缺失的时分秒——
  晚上 21:25 跑，两个边界都变成"那天 21:25"：`--since` 丢掉周一当天 21:25 前的提交，
  `--until` 又把下周一白天的提交捞进来（实测同一周 118 条会跑成 128 条、82 条会跑成 68 条，
  而且不报任何错）。边界跟着运行时刻漂移，是这份报告最隐蔽的错误来源
- `--until` 是**开区间**，写 `--until="2026-09-28 00:00:00"`（周日 +1 天），否则会漏掉周日一整天
- **跑完两头各瞄一眼**：`--format='%ad' --date=iso` 的第一条和最后一条都应落在周一~周日之间；
  最早一条没到周一、或最新一条跑进了下周一，说明时间窗被"现在几点"带偏了
- 报告首行把口径写出来：`项目报告（2026-09-21 ~ 2026-09-27）`——日期算错时用户一眼就能发现

### 第 3 步：拉取全部提交（不按作者过滤）

对每个目标仓库：

```bash
git -C <repo-path> log --since="<周一> 00:00:00" --until="<周日+1天> 00:00:00" --no-merges \
  --date=short --format="%h|%ad|%s"
```

- **不加 `--author`**，这是本 skill 的核心：项目报告回答的是"项目这周往前走了多少"，不是"我干了多少"
- **也不取 `%an` / `%ae`**：谁的提交都一样算数，取出来只会诱使你往报告里写人。
  少一个字段，少一处需要确认的东西
- 默认 `--no-merges`：合并提交只是把已有改动集成一次，算进来同一件事会被数两遍
  （口径里写"不含 merge"；用户要看合并记录时再补一条含 merge 的统计，别混着报）
- **只看当前分支**，本地判断不了远端有没有新提交：`git status -sb` 只跟本地的 remote-tracking ref 比，
  那个 ref 可能是几天前 fetch 的。所以别假装能检测落后，直接在口径里注明
  "基于本地 master"，并附最后的 fetch 时间（`stat -f %Sm .git/FETCH_HEAD`，macOS），
  拿不准就问用户要不要先 `git fetch`——**不要偷偷联网**
- 仓库路径不存在 → 跳过并标注，不要静默略过
- 仓库在但当周无提交 → 报告里这个项目仍然保留，进展写"本周无提交"（非本周区间就写"该区间无提交"），
  别把它删掉：用户指到这个路径就说明他关心，"没动静"本身就是他要的信息
- **所有目标仓库在整个窗口里都没有提交**时，先把这件事告诉用户并给出选项：
  "这个区间三个仓库都没有提交，要不要换个区间（比如最近一个月）？"；
  用户不在场或说了就按这个区间出，那就照实出一份进展写"无提交"的报告（见示例 2），
  不要为了凑内容往回翻历史提交

### 第 4 步：monorepo 子应用归类

判定标准是"这个仓库里确实有多个能独立交付的子应用"，**光有 `pnpm-workspace.yaml` 不算数**：
有的单应用仓库也放这个文件（只用来配 allowBuilds、lint 范围之类），照它拆会拆出一堆前缀空气。
硬证据是这两条之一：

- 有 `apps/` 或 `packages/` 目录（反例：见过只有 `pnpm-workspace.yaml` + `src/` 的仓库，
  那是把 workspace 文件当配置文件用了，本质单应用 → 按普通仓库处理，不加前缀）
- `pnpm-workspace.yaml` 的 `packages:` 字段里声明了多个包路径

判定成立后：

1. **先看提交 scope**：`feat(app-a): ...` → app-a 子应用
2. **scope 一律用文件路径复核，别直接信它**：scope 是提交的人自己填的，很可能是页面名、模块名。
   实测 `refactor(report): ...`、`feat(login): ...`、`refactor(home): ...` 的改动全在
   `apps/app-a/` 下（`apps/<x>/pages/...`），照 scope 写就会冒出 report、login、home
   三个不存在的子应用。复核别一个 hash 跑一次，两条命令就够：

   ```bash
   # 1) scope 分布：一眼看出这个仓库的 scope 是不是"满天飞"
   git -C <repo> log --since="<周一> 00:00:00" --until="<周日+1> 00:00:00" --no-merges \
     --format="%s" | sed -n 's/^[a-z]*(\([^)]*\)).*/\1/p' | sort | uniq -c | sort -rn

   # 2) 提交 → 改动文件：按 @@ 分段看 apps/<x>/ 、packages/<x>/ 前缀
   git -C <repo> log --since="<周一> 00:00:00" --until="<周日+1> 00:00:00" --no-merges \
     --name-only --format="@@%h %s"
   ```

   scope 与路径打架时**以路径为准**；路径跨多个子应用且没有主次的，按改动最多的那个归类，
   或者并进【工程化】
3. **`packages/<pkg>/` 算不算子应用看内容**：能用一句话说清它交付了什么（如 `pkg-components` 组件库）
   就单列，纯工具包、配置包并进【工程化】
4. **归不了类的**（全仓格式化、依赖升级、CI 配置、部署脚本、文档）→ `【工程化】`；
   只有一两条这种零散改动时省略也可以，不要为了凑齐类别硬写一条
5. 条目写成 `【子应用】工作项`，**同一子应用的条目排在一起**，读起来自然成组，不用再加一层子标题
6. 不是 monorepo 就不加前缀
7. **拆错了要能看出来**：如果所有条目都落进同一个子应用、或者一条都归不了类，
   说明这仓库其实是单应用，去掉前缀重来，别硬着头皮写

### 第 5 步：把提交提炼成进展条目

1. **合并同类**：多人、多条提交绕着同一件事 → 一条。项目报告比周报更该合并，
   因为数据源是全部人的提交，不合并会变成流水账
   - `refactor(app-b): 替换ProForm组件为原生AntD组件` + `替换ProComponents组件为自研UI组件`
     + `移除ProComponents依赖，改用原生Ant Design组件` + 同类 2 条 →
     `【app-b】ProForm/ProTable 全量替换为原生 AntD 组件`
2. **翻译成业务语言**，不要照搬 commit message：
   - `refactor(report): 图层筛选区域/类型二级联动 + 面板紧凑化` →
     `【app-a】图层筛选改二级联动，面板紧凑化`（注意 scope 是模块名，实际归属 app-a）
   - `fix(app-b): 修复懒加载树勾选状态丢失问题` → `【app-b】修复懒加载树勾选状态丢失`
   - `chore: app-a 部署脚本` → `【工程化】更新 app-a 部署脚本`
3. **每条不超过 30 字**，参数、环境名、接口名这类细节该删就删（`0.5m` 改成 `500m` 这类保留）
4. **排序分两层**：子应用之间按提交量和重要性排；同一个子应用内部按
   主要功能 > 布局与交互优化 > 重构 > bug 修复 > 杂项——别为了按类型排，把一个子应用的条目拆得七零八落
5. **控制条数**：每个项目 3–10 条（子应用多的 monorepo 最多 12 条）。有 100 多条提交的项目，
   写 8–12 条是正常的，写 30 条是把统计工作推给了读者。
   要砍先砍零散改动（只有单条修复的子应用、部署脚本），但**别把整个活跃子应用砍没了**：
   有功能开发的子应用至少留一条；砍掉的量在口径里交代一句（"另有 N 条零散提交未逐条列出"），
   读者才知道这份报告的边界在哪

### 第 6 步：补齐 git 看不到的内容

git 只能给出"进展"，风险和计划必须问用户，不许自己填：

- **风险/问题**：联调卡住、需求变更、等后台接口、测试环境不可用、人力被抽走
  > Gmi 本周有什么风险或者卡点吗？没有我就写"无"。
- **下周计划**：
  > 下周这几个项目分别要做什么？简单说一句就行。

**提问节奏**：需要问用户的主要是三件事——项目、时间区间、风险与下周计划。
项目没定下来之前别问后面的（问错了全白问）；能合就合，一轮问完比来回几轮强：

> Gmi（09-14 ~ 09-20）118 条提交，有什么风险或卡点吗（没有我就写"无"）？
> 下周 Gmi 打算做什么？

用户没给计划时写"（暂无，待补充）"，不要从提交里推测。顺带问一句有没有非编码进展
（评审、汇报、部署、培训、面试）——有就按项目并入对应项目的进展条目，**别为它新开字段或新开项目**；
没有就什么都不加，模板不变。
**问不到用户时**（无人应答、批量跑）不要卡住：照常把问题列出来，字段先用占位
（"无" / "（暂无，待补充）"），并在报告末尾附一份"待确认"清单——留白比编造强。

### 第 7 步：生成并确认

1. 按模板输出完整报告
2. 顺带把**口径**给用户核对一遍：项目 / 时间区间（写全时分秒）/ 提交数（注明不含 merge，
   以及未逐条列出的零散提交数）/ 分支与最近 fetch 时间
   （口径是防止"少数了一个仓库""周一被丢了"这类错误被带进正式汇报的唯一手段）
3. 用户确认后定稿；**默认在对话里输出，用户要存文件再存**

## 示例

下面的示例数字来自一个真实周的快照，只对得上那一周；子应用、仓库名做了脱敏（`app-a`、`repo-a` 之类），
你本地叫什么就是什么。**照它的格式，不要照抄内容**，每次都要自己跑一遍 git 拿当次的数字。

**示例 1：用户直接给路径（真实形态）**

> 帮我出一下 ~/Documents/GitLab/Gmi 的项目报告。

`~/Documents/GitLab/Gmi` 是 monorepo（`pnpm-workspace.yaml` + `apps/`），这一周 118 条提交。
提交里出现的 scope 有近 20 个，但路径复核后：`login`、`report`、`home`、`map` 这些模块名 scope（共 8 条）
和 `service, warn`（1 条）全在 `apps/app-a/` 下，`admin`（1 条）其实是 `apps/app-b/`——
照 scope 直译能凭空多出 8 个子应用。按路径归位后，提交量集中在 app-b（31 条）、app-c（17 条）、
pkg-components（10 条）等几个子应用上。下面是合并后的节选（完整口径见报告末尾）：

```
项目报告（2026-09-14 ~ 2026-09-20）

一、Gmi
本周进展：
1. 【app-b】ProForm/ProTable 全量替换为原生 AntD 组件
2. 【app-b】修复懒加载树勾选状态丢失与进度条渲染
3. 【app-b】限制数据出库、删除权限，调整部门数据刷新逻辑
4. 【app-c】新增服务资源管理页面，完善卡片与操作区交互
5. 【app-c】初始化项目源码，新增测试环境构建脚本并拆分配置
6. 【pkg-components】抽离公共 iframe 组件并统一页面实现
7. 【app-f】配置新增数据项，默认认证类型改为 private
8. 【app-h】修复首页双滚动条
风险/问题：无
下周计划：（暂无，待补充）

口径：Gmi @ master（本地，最近 fetch 09-24 22:02），09-14 00:00:00 ~ 09-21 00:00:00，
118 条提交（不含 merge；含 merge 138 条）；未逐条列出 52 条（以其它子应用与无 scope 的改动为主）
```

118 条提交最后只留 8 条，这才是正常比例：app-b 的 31 条合并成 3 条，改动少的子应用各留一条，
部署、依赖、打包这类零散改动并进同类条目或省略；剩下的 52 条不再逐条列，在口径里交代一句就够。
**报告是给人看状态的，不是给人做审计的。**

这个例子顺带是时间窗的反面教材：同一周只写日期跑出来是 128 条，不是 118——
`--since="2026-09-14"` 按"现在几点"补成 21:25，把 09-14 当天 21:25 前的 4 条丢了；
`--until="2026-09-21"` 同样补成 21:25，把下周一 09-21 白天的 14 条捞了进来。
**两个边界都会随运行时刻漂移**，所以时分秒必须写全（见第 2 步）。

**示例 2：给的路径是个目录（里面不止一个仓库）**

> 出一下 ~/Documents/GitLab/<多仓库目录> 的项目报告。

这个目录本身不是仓库，底下挂着三个（示例里叫 `repo-a`、`repo-b`、`repo-c`），这一周都没有提交。
先说明统计范围，再照实出报告——进展只能写"无提交"，不是省略，也不是往回翻历史凑内容。

```
~/Documents/GitLab/<多仓库目录> 下面有三个仓库，我按这一整个目录统计：
1. repo-a
2. repo-b
3. repo-c
```

```
项目报告（2026-09-14 ~ 2026-09-20）

一、<多仓库目录>
本周进展：
1. 本周无提交
风险/问题：无
下周计划：（暂无，待补充）

口径：repo-a / repo-b / repo-c @ master（均本地），09-14 00:00:00 ~ 09-21 00:00:00，0 条提交
```

要不要换个区间看看（比如最近一个月）？还是只看其中某一个仓库？

如果 `find` 下来一个仓库都没有，就直接说"这个目录下没有 git 仓库"，不要拿别的项目顶上。

## 注意事项

- **路径是唯一入口**：只统计用户给的那个路径（及其下的仓库），绝不顺手把别的项目也写进去；
  没给路径就问，**不要自己去 `~/Documents/GitLab` 下扫一遍**
- **不加 `--author`，也不写人**：按作者过滤就退化成了周报；把提交人写进报告同样跑偏——
  这份报告只回答"项目走到哪了"
- **口径先确认再定稿**：时间区间、分支、仓库是否齐全，这三样错了，报告写得再好也是错的
- **时间窗写全时分秒**：`--since="<周一> 00:00:00"`、`--until="<周日+1天> 00:00:00"`。只写日期时两个边界
  都会拿"现在几点"补时分秒：`--since` 丢掉周一白天的提交，`--until` 又把下周一的提交捞进来
  （实测同一周 118 条跑成 128 条、82 条跑成 68 条），静默无报错；`--until` 还是开区间，
  忘了 +1 天就丢周日整天
- **口径要能自证**：提交数注明含不含 merge，砍掉的零散提交说明条数，分支和最近 fetch 时间写上——
  口径就是这份报告的可信度边界
- **合并优先于罗列**：100 多条提交 → 10 来条进展；读者要的是项目状态，不是 commit 流水账
- **不要编造**：进展只来自 git 提交和用户描述；风险、下周计划、非编码工作一律问用户
- **报告里不出现人名**：不写"谁做了什么"，也不列参与人名单——给项目出报告不需要认识人
- **空项目也要留字段**：本周无提交写"本周无提交"，风险写"无"，计划写"（暂无，待补充）"
- **合并提交不算数**：默认 `--no-merges`，否则同一批改动会被数两遍
- **别偷偷联网**：本地判断不出远端有没有新提交（`git status -sb` 只跟本地 ref 比），
  口径里注明分支和最近 fetch 时间，拿不准就问用户要不要 fetch
- **提交数是数出来的**：报告和口径里出现的任何数字都必须来自 git 命令的实际输出
