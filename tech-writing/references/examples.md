3. **文字的量始终压着**。全篇 306 行，最长的连续散文是那四版代码之间的说明，每段一到两句。

### 骨架标注

| 位置 | 原文 | 这一步在干什么 |
|---|---|---|
| 标题 | `# 图层约定` | **三个字**。不写"图层配置规范说明" |
| 开场 | （无） | **`#` 下面直接第一个 `##`**，没有一句引言 |
| 每节标题 | 配置 / 创建图层 / 图例 / 图层列表 | **标题就是这条规则管的东西**，不是"规则一" |
| 每条规则 | 图层配置属性以[api文档](链接)为准，可以加自定义属性。 | **一句，带一个链接**，告诉读者权威出处在哪 |
| 默认 + 例外 | 默认都展示图例；无须展示的，请设置`legendEnabled: false`。 | **这是规范文档最好用的句式**，一次说清默认行为和退出方式 |
| 结尾 | （无） | 最后一条规则写完就结束 |

**最值得学的一点**：最后两节用了**完全相同的句式**（`默认都……；无须……的，请设置X`）。在规范文档里，重复句式是优点不是缺点，读者扫一眼就知道去哪儿找例外。

**注意分号**：`默认都展示图例；无须展示的，请设置…` 这里是分号不是句号。全语料 `；` 很少用（博客 4 次），基本都出现在这种"默认 + 例外"的对照句里。

**原文**：`chu/docs/philosophy/lint.md`（全文 11 行，散文 6 行，零代码块）

```markdown

本来想继续沿用umi的[lint规则](https://umijs.org/docs/guides/lint)，即[umi/lint](https://github.com/umijs/umi/tree/master/packages/lint)。

但是umi/lint 不支持eslint9，也[没工夫升级](https://github.com/umijs/umi/issues/12261)。

最后使用的阿里的前端规约[eslint-config-ali](https://github.com/alibaba/f2e-spec)，因为它文档依据写的很好。

并没有添加太多的配置，主要是忽略掉ArcGIS JS 的静态文件和Umi的运行文件，详见[eslint.config.js](https://github.com/GeoDaoyu/Chu/blob/main/eslint.config.js)。
```

### 骨架标注

```
本来想 A（+ A 的文档链接）
但是 A 有毛病（+ issue 链接）
中途试过 B 和 C（+ 各自链接）
最后用 D，因为它 E（+ D 的链接）
并没有额外做什么，主要是 F，详见 [文件](链接)
```

### 为什么这篇是范本

1. **六个转折，五个链接。** 每一个被提到的方案都有一个链接，读者能自己去看。写决策记录最容易漏的就是这个。
2. **淘汰原因具体到可验证**：`不支持eslint9`，不是"跟我们的技术栈不太契合"。
3. **理由朴素得理直气壮**：`因为它文档依据写的很好`。这就是完整理由，不需要包装成"生态成熟、社区活跃、长期可维护"。
4. **一句情绪，恰到好处**：`也没[工夫升级](链接)`。五个字，真实，不装。整篇就这一处。
5. **结尾交代实际做了什么**：`并没有添加太多的配置，主要是忽略掉…`。决策记录不能只讲选型，还要讲落地。

### 语气上的分寸

- **不审过去**：`本来想继续沿用` 是陈述当时的想法，不追加"现在想想当时太天真"。
- **不吹现在**：`并没有添加太多的配置`，是收着说，不是 `这套方案非常优雅`。

有时，flex 子元素的内容很长，会把容器撑开，出现横向滚动条。

原因是子元素的`min-width`默认是`auto`。

<!-- more -->
## 现象

（截图）

```html
<div class="box">
  <div class="item">一段很长的文字</div>
</div>
```

```css
.box {
  display: flex;
}
```

## 解决

给子元素设置`min-width: 0`：

```css
.item {
  min-width: 0;
}
```

> 注：`min-height`也有同样的问题，在纵向 flex 里要设成`0`。
