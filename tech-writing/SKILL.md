# 技术文档写作 Skill

这个 skill 复刻的是一套**已经量出来的**写法，不是模糊的"简洁风格"印象。语料是作者自己的 **66 篇**技术文字（47 篇博客 + 19 篇框架文档），两个来源量出来的数字几乎一致：

| 指标 | 实测值 | 意味着 |
|------|--------|--------|
| 代码行 ÷ 散文行 | **约 8 : 2** | 文章的主体是代码和配置，文字是给它们搭的台子 |
| 单句段占比 | **90%（博客）/ 83%（文档）** | 一句一段。这是最好认的特征 |
| 句子中位长度 | **22 字（博客）/ 20 字（文档）** | 短句铺底，长句只在需要解释时出现 |

把这三条做对，文章就有七分像了。剩下的在下面的规则和 `references/` 里。

**两条压在所有技法之上：**

1. **不留错别字。** 出稿前必须通读校对一遍。技术文档里一个错字或病句会直接降低整篇的可信度，读者会开始怀疑你的代码是不是也这样。语料里确实有错别字，**那是要修掉的毛病，不是要模仿的风格**。
2. **不编事实。** 版本号、报错文本、接口字段、文件路径，要么是用户给的，要么问过，要么写成 `<占位>`。

**还有一条，先说**：这套文风的力量来自**不修饰**。原文里没有一句是"为了好看"才写的，每一句都在交代事实、引出代码、或提醒一个坑。如果写的时候产生"这句写得真漂亮"的念头，删掉它。

> 下文说「语料」都指作者的 66 篇技术文字。所有「零次」「只有 N 篇」的断言都以此为口径，量测方法见 `references/corpus-notes.md`。

## 一、先问，还是先写

用户给的通常只是一个念头（"今天踩了个 CSS 的坑，想写一篇"）。这时候**先问，但只问会写错的东西**。

### 只问事实，不问写法

会写错的东西 = 你自己编不出来的技术事实：

- **现象**：具体报错 / 错误表现是什么，能不能复现
- **原因**：根因是什么（或者：是不是还没查出来）
- **环境**：版本号、系统、框架
- **结论**：最后用哪个方案解决的
- **背景**（写设计文档时）：要解决什么问题，有哪些约束

**不要问**结构、语气、分几节、标题叫什么、开头怎么写，这些由这个 skill 决定。问这些既浪费用户时间，也说明你没读这篇文章。

### 提问的规矩

- **一次问完，最多 3 个**，放在一条消息里，别挤牙膏。
- **能推就推，推不出来才问**。用户说"改了 `dbms.connectors.default_listen_address` 就好了"，就不用再问根因了。
- **他也不知道的，就别追问**。写排查记录时，文章在"他查到哪一步"结束是**正常的**，不要把文章撑到有结论为止。
- **剩下的小缺口用占位符**：写 `<你的报错信息>`、`<版本号>`、`<实际路径>`，**绝不编造**。

用户已经把现象、原因、环境都说了，就直接写，别为了走流程硬问三个问题。

## 二、六类文档，六套骨架

判断类型看**用户手里是什么**，不是看话题。

| 用户给的东西 | 类型 | 篇幅 |
|---|---|---|
| 一个模块 / 一套机制的设计，要讲清楚 | **设计文档** | 长 |
| 一组要同事遵守的规则 | **约定与规范** | 短到中 |
| 一个"当初为什么选 X" | **决策记录** | 短 |
| "怎么装 X" / 一套要照着做的流程 | **教程步骤** | 中 |
| 一个报错 / 一个显示异常 / "排查了半天" | **踩坑记录** | 短 |
| 一个小知识点 / "顺便记一下" | **备忘速记** | 很短 |

只有类型确实模糊时才混合两套骨架，否则不要贪多。

### 1. 设计文档（含方案实现）

讲清楚"要解决什么、怎么设计的、怎么实现的"。这是最需要结构的一类。

```
## 需求 / 背景     ← 要解决什么问题。可以是一串并列的条目
## 考虑            ← 有哪些约束、哪些路被排除了（可选）
## 设计思路        ← 一段话讲清核心机制（一般到这就够了）
## 实现过程        ← 按模块拆：store / lib / widgets / app
## 高阶            ← 进阶用法（可选）
## 多实例          ← 边界情况（可选）
## 附件            ← 完整代码或数据结构（可选，很长才有）
```

- **标题按模块名起，不按"第一步第二步"**：`### store`、`### lib`、`### widgets`、`### app`。
- 实现过程里，每节就是**一句机制说明 + 一段代码**。机制说明可以到 2 句，这是唯一允许段落稍长的地方，因为读者要理解设计。
- **先破后立是这个类型的强力手法**（见第三节）：先把笨写法摊开，再逐条加需求让它烂掉，最后才给方案。作者的 `使用中间件解耦业务流函数` 就是这么写的，全语料有 5 个独立实例。

### 2. 约定与规范

一组"请这么做 / 无须那么做"的规则。特点是**短、可执行、每条配一个示例**。

```
# 图层约定

（一句话说这个约定的适用范围）

## 配置

（一条规则 + 代码或默认值）

## 创建图层

（一条规则 + 代码）

## 图例

默认都展示图例；无须展示的，请设置`legendEnabled: false`。
```

- **一条规则一个 `##`**，标题是这条规则管的东西（配置 / 创建图层 / 图例 / 同步）。
- 规则句式固定：**默认怎么样；不需要的，请设置 X**。见下文「规定语气」。
- 每条严格控制在一两句。规范文档不该有议论。

### 3. 决策记录

回答"当初为什么这么选"。作者最独特的一类文字。

```
# 编码规范

本来想继续沿用umi的[lint规则](链接)。
但是umi/lint 不支持eslint9，也没[工夫升级](链接)。
中途使用过其他支持eslint9的热门开源配置：xo和@antfu/eslint-config。
最后使用的阿里的前端规约eslint-config-ali，因为它文档依据写的很好。
```

四拍：**本来想 A → 但是 A 有毛病 → 中途试过 B/C → 最后用 D，因为 E。**

- 讲清楚每个方案**被淘汰的具体原因**，不是笼统的"不适合"。
- **说清楚就是好理由**：`因为它文档依据写的很好` 就够了，不用拔高到工程哲学。
- 可以带一点情绪：`也没工夫升级`、`幸好Umi提供了一些方式`。这是人味，不是不专业。

### 4. 教程步骤

```
## 环境准备    ← 前置条件，版本号写清楚
## 创建项目
## 启动项目
## 部署发布
```

- 标题用**动作名**（环境准备 / 创建项目 / 启动项目 / 部署发布 / 下载 / 解压 / 启动 / 验证），2–4 字。
- 长流程用 `## 1` `### 1.1` 编号；五步以内不用编号。
- 每一步是**一句话 + 一段命令**，先说要做什么，再给代码，顺序不颠倒。
- **一行结论收尾每节**：`输出OpenJDK的信息。` / `能浏览、拷出、写入、删除。` 不说"命令执行成功后我们可以看到如下输出"。
- **尾部提醒**用「记得X」的短句挂着：`记得重启。` / `记得忽略git`。
- 允许省略：不重要的环节直接写"这里不细说"。

### 5. 踩坑记录

```
## 问题 / 现象     ← 一句话把问题说清，配图或报错
## 调试 / 排查     ← 按顺序写试了什么、排除了什么
## 原因            ← 一两句。说清就够，不展开原理
## 解决方案        ← 代码或配置。这是全文重心
```

- **试错的弯路是资产**。排除过的错误方向要写出来（`写测试页面调试，发现是…`），读者会遇到同样的事。
- 多解时直接列：`法一：…` `法二：…` `法三：…`。**不比较优劣，除非用户问了。**
- 没查到根因就停在"目前用 X 绕过了"，不要补一段编的原因。

### 6. 备忘速记

最短的一类，常常整篇不到 20 行散文。适合放进 FAQ 或独立成篇。

```
（一句话说这个代码是干嘛的）
（代码）
参数说明：
+ `参数`— 说明.
+ `参数`— 说明.
> 注：（可选，一个容易踩的点）
```

**`参数说明：` 的格式**：冒号结尾、`+` 列表、参数名用反引号包住、后面跟全角单破折号 `—`、每条以 ASCII 句点结尾。这是语料里稳定复现的写法（约 12 次）。

## 三、落笔规则

### 开场：冷启动

从第一句话就是内容，没有暖场。

> 不使用插件，通过CSS设置滚动条样式。
>
> 项目中有使用到视频融合，记录实现过程。
>
> 某项目，在内网的统信（Linux）系统下安装neo4j。
>
> Chu使用的地理引擎是[ArcGIS Maps SDK for JavaScript](链接)。它是一个十分优秀的地理引擎，功能强大。
>
> 目录树的功能是多变的，可能以下的功能都需要实现

四条铁律：

- **不许有"大家好""今天我们来聊聊""众所周知""随着……的发展"**。语料零出现。
- **第一句就交代场景**（什么项目、什么需求、什么现象），不要先讲背景意义。
- **最多铺垫 3 句就进正文**。有 `## 背景` / `## 需求` 节时，那一节本身也可以只有一句话。
- 文档常以 `# 标题` 直接开头，博客则常用 `## 背景`。两种都对，看类型。

### 段落：一句一段 + 四拍节奏

这是最好认的特征。**83–90% 的段落只有一句**。默认动作是**换行**，不是接着写。

段落之间有一个反复出现的四拍原子：

```
问题句  →  反向句  →（代码）→  结论句
```

> 有时候加个border-left，可以有分割的效果。
>
> 但是直接设置，高度顶满之后，感觉不好看。
>
> （代码）
>
> 所以通过before来插入一个元素，就可以控制高度，更好看些。

四句各自独立成段。**先立、再破、给代码、一句收。**

> 例外只有一个：**设计文档里解释机制**时，可以到 2 句（`store 管理 checkedKeys 和 treeData 状态，通过 subscribeWithSelector 监听变更。checkedKeys 变更后委托给 layerControl 对象处理…`）。超过 2 句就拆。

### 句子：短句铺底，长句解释

- 默认写**十几二十字**的句子（中位 20–22，均值 27）。一成在 8 字以内，两成在 40 字以上。
- 需要交代因果、条件、细节时才拉长，**一个长句后面要跟一个短句**来收。
- **主语尽量省**。命令、步骤、现象、机制说明都不需要主语；连诊断句都是无主语的：`受到高程影响，导致部分面要素被遮盖。`
- **人称按语域分**：
  - **博客**：`我` 讲自己做的事（`我翻译并简单修改了官网的部署教程`），`你` 只在给操作指引时出现（`你可以使用以下伪元素选择器`）。
  - **文档**：`我` **零次**，`你` **零次**。主语换成**产品或模块名**（`Chu使用的地理引擎是…` / `Chu禁用了Umi的默认布局`），或者干脆**省略主语**（`采用了Monorepo架构来设计代码仓库。` / `store 管理 checkedKeys 和 treeData 状态。`）。
  - 两边都极少用 `我们`（散文里合计 4 次），且**从不用来指"读者和我"**，只出现在 `> 我们约定view的domId为"view"。` 这种约定句里。
- **`大家`、`笔者`、`咱们`、`你们` 语料零出现。** 不要用。
- **观点句不用对冲**：`ramda的写法明显要更复杂一些。` 而不是"我个人觉得 ramda 的写法可能会更复杂一些"。`可能` 只用于技术不确定性（`可能需要考虑路径指向。`）。

### 引出代码：引导句越短越好

代码块前面的句子，绝大多数是**2–15 字，以 `：` 结尾**。六种模板：

| 模板 | 原文例子 |
|---|---|
| 光杆名词 + `：` | `参数说明：`（8 次）`代码如下：` `请求示例：` `示例代码：` `样式示例：` |
| `X如下：` | `转换的格式如下：` `效果图如下：` `引入方式如下：` `示例核心代码：` |
| `下面……` | `下面列两种CSS处理文字溢出的方式，分别针对单行文字和多行文字。` `下面是一些微件开发源码示例：` |
| `先/然后/接着 + 动词` | `先放上平时的写法：` `使用ramda的代码实现如下：` |
| **文件路径 + `：`**（文档常用） | `` `packages/lib/src/core/layer/createLayer.js`： `` `LayerTree.jsx`： `apps/scene-pro/src/widgets/Map/index.js`： |
| 动作短句（可无冒号） | `拷贝到服务器/opt下，进行解压，然后删除压缩包` `记得忽略git` |

不要写"接下来我将为大家展示一段示例代码，这段代码的作用是……"。**一句话说清这块代码是什么，然后换行给代码。**

代码块后面通常**不解释**。要解释就走这三条路：

1. **`参数说明：` + 列表**，格式 `` + `参数`— 说明. ``
2. **中文注释写进代码里**。他甚至会明说：`参数说明写到了代码注释中。`
3. **设计文档里可以补一句机制说明**（一句，不是一段）

**展示运行结果时不要贴原始输出**，用一句话下判断：

> 输出OpenJDK的信息。
> 结果：无报错，不上图。
> 能浏览、拷出、写入、删除。

### 规定语气（约定与规范类专用）

文档里要同事照做的规则，用这套句式。**`建议` 在 66 篇里零出现**，`应该`、`禁止`、`务必` 也是零，`推荐` 只有 4 次且**一律出现在括号或目录树注释里**（`（推荐用 nvm 来管理 node 版本）`、`// 推荐目录`），从不做独立祈使句：

| 场景 | 句式 | 原文 |
|---|---|---|
| 定默认行为 | `默认都……；无须……的，请设置 X` | ``默认都展示图例；无须展示的，请设置`legendEnabled: false`。`` |
| 定唯一做法 | `不使用 A，而是统一使用 B` | ``**不使用`.umirc.ts`，而是统一使用`config/config.js`**`` |
| 沿用时 | `沿用 X 的 Y` | `权限沿用Umi的[access](链接)。` |
| 立约定 | `> 我们约定……` | `> 我们约定view的domId为"view"。` |
| 给出处 | `以 X 为准` | `图层配置属性以[api文档](链接)为准，可以加自定义属性。` |
| 强调必做 | `必须`（很少，散文里全语料 3 次） | `所以必须使用[pnpm](链接)。` |
| 硬规则 | **加粗整句**，不配 `请` | `**不使用`.umirc.ts`，而是统一使用`config/config.js`**` |

**语气是平视的**：不解释为什么（除非真有必要），不反复强调，不写"请注意务必"。规则本身就是权威。

### 目录树

贴目录树是高频动作。约定：

```
Chu
├─ apps
│  ├─ map-pro
│  └─ scene-pro
│     ├─ .umirc.ts
│     └─ src
├─ packages
│  └─ ui
└─ pnpm-workspace.yaml
```

- 用 `├──` `└──` `│`，每层缩进 3 个空格（`│   ├── x`）。仓库总览那棵树可以用细的 `├─`，同一篇里保持一致。
- **注释用 `//` 右对齐挂在同一行**，说明这一项是什么：

```
├── components                          // 微件内部的组件
├── images                              // 图片，一般是用在样式的图片
├── viewModel.js                        // 分析工具对应ViewModel
├── index.(js|jsx)                      // 主文件
└── index.less                          // 样式文件
```

- 多个可选的扩展名写成 `index.(js|jsx)`。
- 代码块语言标 `plain` 或 `text`。

### 注：和引用块

`>` 引用块在语料里有四个用途：

1. **提醒一个坑**（**博客专用**，语料里 4 次；**文档里 `注：` 零次**）：``> 注：如果不设置`background-clip`，在border有透明度的时候，会透到下面的background。``
2. **立约定 / 补一个前提**：`> 我们约定view的domId为"view"。` / `> 文件加载完全会继续加载umi.js，所以在这里加载的js不支持异步。`
3. **引一段官方定义**（常配一个链接）
4. **一句自我坦白**：`> 我不知道猴耳环和感冒灵会不会药物冲突或者药物过量，所以只敢分开吃`

第 4 类很重要：**不确定就说不确定**，从不假装权威。

### 标题：写具体内容，不套模板

语料里 200 多个二级标题，绝大多数是独一份的。**标题是这篇文档的实际内容，不是从模板里挑的。**

**标题很短**，中位 2–4 字：

- 结构槽位：`背景`（最常用）、`需求`、`考虑`、`设计思路`、`实现过程`、`实现基础`、`期望`、`核心`、`调用`、`延伸`、`附件`、`过程`、`步骤`、`验证`、`坑`、`参考链接`
- 动作名：`下载`、`解压`、`环境变量`、`编译`、`启动`、`创建项目`、`部署发布`
- 模块名：`store`、`lib`、`widgets`、`app`、`Map`、`Calcite`
- 具体问题名：`WMTSLayer加载失败`、`配置wss`、`ip监听`
- 文件名式：`依赖：pom.xml`、`配置类：WebSocketConfig.java`

**坏**：`## 问题分析`、`## 总结与展望`、`## 深入理解并分析中间件模式在业务流解耦中的实际应用`。

**标题数量中位 3 个**，章节长度是**悬殊的**（有的 19 节，有的 2 节）。不要为了结构对称硬凑小节。

### 结尾：直接停

**绝大多数文章没有结尾节**（66 篇里只有 4 篇有 `结束语`/`结语`/`使用总结`）。最后一步做完、最后一个代码块或截图贴完，文章就结束了。

真要写，就 1–3 句，说一个实在的体会或成本：

> ramda在进行数据处理、数据转换上，流程似乎更加明晰，代码更加可读。
>
> 配置一次项目自动构建大概需要大半天时间。然后后面就不怎么用管它了。

文档类还可以用 **`## 参考链接`** 收尾，把外部资料列成裸链接：

```
## 参考链接

https://developers.arcgis.com/javascript/latest/migrating-to-components/
```

**必须避免**：`希望对你有帮助`、`欢迎留言讨论`、`如有错误请指正`、`感谢阅读`、`综上所述`。语料零出现。
**也不要总结全文**，读者刚看完，不需要你再讲一遍。

### 可以有的那点人味

文风整体是干的，但偶尔会漏出一点，这也是"像他"的地方：

- 一句实在的大白话：`频繁的构建部署，费时烦心，所以学习使用Jenkins来实现自动化。`
- 一个比喻：`在服务器上放了一个"金老头"` / `政务网和内网，还出于手工拷贝部署的刀耕火种中。`
- 一个词的评价：`Nginx作为高性能的Web服务器，小巧、稳定、香。` / `它是一个十分优秀的地理引擎，功能强大。`
- 顺手吐槽：`也没工夫升级` / `幸好Umi提供了一些方式可以获取到routes配置和location。`
- 判断标记：`如果是寄，乌米的发音，就是啾咪，啾咪听着就比较好听了，像亲吻的声音。✔`
- **说自己的方案不好**：`ramda的写法明显要更复杂一些。`

最后一条尤其重要：**方案有代价就写代价**。这种诚实地道，比夸自己高明更让人信。

**但不要刻意制造**。整篇有一个这样的点就够了，硬塞笑话比没有笑话更糟。

### 标点和排版

中文一律全角，英文单词/代码/路径周围保持半角。**这一节里有几条是硬禁令，破一条整篇就不像了。**

**绝对不出现**（语料实测为零）：

| 禁止 | 说明 |
|---|---|
| `——` 破折号 | **零次**。想用破折号的地方，直接断成两句 |
| `……` / `…` 省略号 | **零次**。话没说完就说完 |
| `！` 感叹号 | **零次**。力量来自收着 |
| `*` 项目符号 | 零次。只用 `-`、`+`、`1.` |
| emoji / 颜文字 | 不用。唯一的例外是 `✔` `✘` 这种**判断标记**（`naming.md` 用它们标注发音好不好听），那是内容不是装饰 |
| 开场套话 | 大家好、今天我们来聊聊、众所周知 |
| 结尾套话 | 希望对你有帮助、欢迎留言、如有错误请指正、感谢阅读、综上所述 |
| 过渡套话 | 接下来、下面让我们、首先我们来看、值得一提的是、不难发现 |
| 书面连接词 | 因此、然而、此外、基于此（换成"所以""但是""同时"或直接省略） |
| 人称 | 大家、笔者、咱们、你们 |
| 设问 | 以"……呢？"开场的反问句 |

**这几个高频标点的用法**：

| 标点 | 用法 |
|---|---|
| `：` | **最高频**。代码/列表的引导句一律用它收尾 |
| `，` | 主句读停顿。**逗号密度低**，不要一路逗号连缀成长句 |
| `（）` | **补一句真正的旁注**：`（骨架+衣服）`。别浪费在可有可无的补充上 |
| `~~删除线~~` | 划掉被排除的选项：`- ~~接口：目录树+图层列表，前端构建树~~` |
| `**加粗**` | 少用。文档里是**规则标记**（`**不使用`.umirc.ts`，而是统一使用`config/config.js`**`），博客里基本只用在 UI 标签上 |

**链接**：**行内链接为主**（`[pnpm](https://pnpm.io/)`，语料 46 处）。提到某个文档、API、工具时，把链接挂在名字上。**裸链接只用在两处**：`## 参考链接` 节，和官网下载地址那一行。

**标识符**：配置项、函数名、文件名、字段名**一律反引号**：`` `legendEnabled: false` ``、`` `useStore` ``、`` `checkedKeys` ``。目录树用 ` ```plain ` 或 ` ```text `。

> 完整的标点、列表符号、箭头、代码块语言约定见 `references/style-dna.md`。

## 五、交付格式

- **默认直接把正文给出来**，不要先复述一遍你打算怎么写，也不要附"我用了哪些技巧"。
- 用户说"存成文件""写进文档""写进博客"时，才写 `.md` 文件。路径按用户给的来；没说的话问一句，或者用当前仓库的 `docs/`。
- **写进博客**时（`~/Documents/GitHub/blog/source/_posts/`）才需要 Hexo frontmatter：

```yaml
---
title: 设置滚动条样式
date: 2025-01-15 21:19:40
tags:
- flex
categories:
- CSS
---
（摘要段：1–3 句）
<!-- more -->
（正文）
```

  - 只有这四个字段，没有 `description`、`cover`、`permalink`。
  - `title` **平均 12 个字，不带标点，不用问句**。
  - `categories` **只有一个**，取大领域（`CSS`、`JavaScript`、`Java`、`ArcGIS JS API`、`Linux`、`Ramda`）。
  - `tags` 1–5 个，通常 1–2 个，**常常和 categories 相同**。
  - `<!-- more -->` 放在摘要段之后，2023 年后那些二十来行的速记干脆不写。
- **写进框架文档**时（`chu/docs/`）**不要 frontmatter**，直接 `# 标题` 开头，并在 `docs/index.md` 的对应分类下加一行链接。
- 缺的关键事实：**先问**（第一节）。问完还是缺的，用 `<占位>` 标出，并在正文后单独列一行"待补：X、Y"，不要混在正文里。
