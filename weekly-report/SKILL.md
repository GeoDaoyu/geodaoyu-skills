# 周报生成 Skill

## 周报格式

用户的周报遵循以下固定结构，生成时严格遵循此模板：

```
本周完成工作:
一、[项目名称]
1. [具体工作项]
2. [具体工作项]

二、[项目名称]
1. [具体工作项]
...

本周工作总结:
-

下周工作计划:
一、[项目名称]
1. [计划工作项]
2. [计划工作项]

...

四、其他
1. [杂项]
```

## 格式规则

- **一级分类**使用中文数字：一、二、三、四、五
- **二级条目**使用阿拉伯数字：1. 2. 3.
- **项目名称**保持简洁，通常 2-6 个字
- **工作项描述**简洁扼要，一句话说清楚，不超过 30 字
- **本周工作总结**默认填 `-`（用户通常留空）
- 条目按项目分组，不要把所有内容堆在一个项目下
- 项目按重要程度或工作量的顺序排列
- 通用事务（面试、会议、技术调研等）归入"其他"

## 工作流程

当用户要求写周报时，按以下步骤执行：

### 步骤 1：确认仓库与项目映射

用户会提供项目名称到本地 git 仓库路径的映射。如果用户尚未在本次对话中提供，主动询问：

> 请告诉我各项目对应的本地 git 仓库路径，格式如：
>
> - 项目A: ~/path/to/repo-a
> - 项目B: ~/path/to/repo-b
> - ...

记录下这些映射关系，后续步骤使用。项目名称以用户当前说法为准。

### 步骤 2：确定时间范围

- 确认用户要生成的是"本周"还是"上周"的周报
- 计算对应周的周一（起始）和周日（结束）日期
- 日期格式用于 git log 的 `--since` 和 `--until` 参数：`YYYY-MM-DD`

### 步骤 3：获取 git 提交记录

对每个项目仓库，执行 `git log` 命令获取该用户在当周的提交：

```bash
# 获取指定用户在本周的提交（简洁单行格式）
git -C <repo-path> log --author="<git-user-name>" --since="<monday>" --until="<sunday+1day>" --oneline --no-merges

# 如果只需提交标题
git -C <repo-path> log --author="<git-user-name>" --since="<monday>" --until="<sunday+1day>" --format="%s" --no-merges
```

**关键参数说明：**

- `-C <path>`：在指定仓库目录下执行，不需要 cd
- `--author`：按作者过滤。先执行 `git -C <repo-path> config user.name` 确认 git 用户名
- `--since` / `--until`：日期范围过滤。注意 `--until` 是 exclusive，需要设置为周日+1天
- `--format="%s"`：只输出提交标题
- `--no-merges`：排除合并提交，只看实际工作提交

**容错处理：**

- 如果某个仓库目录不存在，跳过并在报告中标注
- 如果仓库存在但当周无提交，标注"（该仓库当周无提交记录）"
- 如果 `--author` 过滤不到结果，尝试不加 `--author` 查看当周所有提交，手动判断

### 步骤 4：从提交信息提取工作项

将每个仓库的提交信息转化为周报中的工作项：

1. **合并同类提交**：同一功能的多条提交合并为一条工作项（如 3 条关于"漫游功能"的提交合并为一项）
2. **翻译为业务描述**：将技术性提交信息转化为业务层面的工作描述
   - `fix: 修复高亮闪烁问题` → `地图点击高亮功能优化`
   - `feat: add roam control panel` → `场景漫游控制面板开发`
   - `refactor: 接口字段适配` → `配合后台接口变更`
3. **保持简洁**：每条工作项一句话，不超过 30 字
4. **保留技术关键词**：UI、API、bug、URL 等技术术语保留不翻译
5. **按重要性排序**：主要功能开发排前面，bug 修复和优化排后面

### 步骤 5：补充非 git 工作

git 提交只能反映代码工作，还需要询问用户补充：

- 面试、会议、培训等非编码工作
- 技术调研、文档编写等不一定提交代码的工作
- 服务器运维、部署等操作类工作

这些归入"其他"分类，或按用户要求创建对应分类。

### 步骤 6：收集下周计划

git 提交无法反映下周计划，必须询问用户：

> 下周计划做什么？可以按项目简单说一下。

用户可能自己手写，也可能描述后让你整理。

### 步骤 7：生成并确认

- 按模板格式输出完整周报
- 请用户确认内容准确性和完整性
- 用户确认后定稿

## 示例

**用户输入（通过 git 仓库）：**

> 帮我写周报
>
> - 项目A: ~/projects/repo-a
> - 项目B: ~/projects/repo-b

**执行过程：**

1. 确认时间范围：本周一至周日
2. 确认 git 用户名：`git config user.name`
3. 逐个仓库执行 `git log --author --since --until --format="%s" --no-merges`
4. 合并同类提交，翻译为业务描述
5. 询问用户补充非 git 工作和下周计划
6. 生成周报草稿，用户确认后定稿

**用户输入（手动描述）：**

> 这周主要在做项目A的地图模块，漫游功能基本完成了，还在做数据目录树。项目B门户 UI 在改。还面试了两个前端。

**生成输出：**

```
本周完成工作:
一、项目A
1. 场景漫游功能开发
2. 数据目录树功能开发中

二、项目B
1. 门户 UI 优化

三、其他
1. 前端面试

本周工作总结:
-

下周工作计划:
（请补充下周计划）
```

## 注意事项

- **不要编造**：只从 git 提交和用户描述中提取工作内容，不自行添加
- **项目名称由用户定义**：每次使用时以用户提供的项目名称为准，不预设项目列表
- **本周工作总结**默认填 `-`（用户通常留空），除非用户明确提供总结
- **容错友好**：仓库路径不存在或无提交时，清晰标注而不是报错
- **先自动后手动**：优先用 git log 自动生成，再让用户补充非 git 工作和下周计划
- **提交信息是线索，不是定稿**：git commit message 需要翻译成业务可读的工作描述，不要原文照搬
