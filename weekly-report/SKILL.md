# 周报生成 Skill

## 配置

默认扫描以下目录中的 git 仓库（按实际环境修改本节）：

- `~/Documents/GitLab`

如果扫描结果没有覆盖用户提到的项目，再询问用户补充路径。

## 周报格式

用户的周报遵循以下固定结构，生成时严格遵循此模板：

```
本周完成工作:
一、[项目名称]
1. [具体工作项]
2. [具体工作项]

二、[项目名称]
1. [具体工作项]
...

本周工作总结:
-

下周工作计划:
一、[项目名称]
1. [计划工作项]
2. [计划工作项]

...

四、其他
1. [杂项]
```

## 格式规则

- **一级分类**使用中文数字：一、二、三、四、五
- **二级条目**使用阿拉伯数字：1. 2. 3.
- **项目名称**保持简洁，通常 2-6 个字
- **工作项描述**简洁扼要，一句话说清楚，不超过 30 字
- **本周工作总结**默认填 `-`（用户通常留空）
- 条目按项目分组，不要把所有内容堆在一个项目下
- 项目按重要程度或工作量的顺序排列
- 通用事务（面试、会议、技术调研等）归入"其他"

## 工作流程

### 步骤 1：确定时间范围

- 确认用户要生成的是"本周"还是"上周"的周报
- 计算对应周的周一（起始）和周日（结束）日期
- 日期格式用于 git log 的 `--since` 和 `--until` 参数：`YYYY-MM-DD`
- 注意 `--until` 是 exclusive，需要设置为周日+1天

### 步骤 2：自动发现仓库

扫描"配置"一节列出的目录，找出本周有提交的仓库：

1. 递归查找目录下的 `.git`（深度 2-3 层，跳过 node_modules 等依赖目录）
2. 对每个仓库执行 `git log --since="<周一>" --until="<周日+1天>" --oneline --no-merges` 统计本周提交数
3. 只保留本周有提交的仓库，列出给用户确认，并询问是否还有其他仓库或目录

注意：周报中的项目名称直接使用仓库名；monorepo 仓库使用子应用（app）名。

### 步骤 3：确认提交作者身份

1. 对每个仓库执行 `git -C <repo> config user.name`（本地配置优先，自动回退全局配置）
2. 收集所有身份，输出"仓库 → 身份"清单，与用户确认哪些身份属于本人
3. 记录本人身份列表，后续 `--author` 过滤使用

### 步骤 4：获取 git 提交记录

对每个仓库，用确认过的身份过滤本周提交：

```bash
git -C <repo-path> log --author="<git-user-name>" --since="<monday>" --until="<sunday+1day>" --format="%s" --no-merges
```

**容错处理：**

- 仓库目录不存在 → 跳过并在报告中标注
- 仓库存在但当周无提交 → 不列入列表

### 步骤 5：monorepo 拆分

仓库是 monorepo（存在 `pnpm-workspace.yaml`，或同时有
`apps/` 和 `packages/` 目录）时，按子应用拆分：

1. **优先看提交 scope**：conventional commits 形如 `type(scope): subject`，scope 就是
   子应用标识。如 `feat(app-a): ...` 归属 app-a 应用，
   `refactor(services): ...` 归属 services 包
2. **scope 缺失时看文件路径**：执行 `git show --name-only --format="" <hash>` 查看改动
   文件，根据 `apps/<app>/` 或 `packages/<pkg>/` 前缀判断归属
3. **归属不了的提交**（全仓格式化、依赖清理、CI 配置、文档等）归入"工程化/公共"类别，
   或并入"其他"，不要硬塞进某个子应用
4. 周报中每个子应用单独成"项目"分组，项目名直接用 scope 名（即 app 名）

### 步骤 6：从提交信息提取工作项

将每个仓库的提交信息转化为周报中的工作项：

1. **合并同类提交**：同一功能的多条提交合并为一条工作项（如 3 条关于"漫游功能"的提交合并为一项）
2. **翻译为业务描述**：将技术性提交信息转化为业务层面的工作描述
   - `fix: 修复高亮闪烁问题` → `地图点击高亮功能优化`
   - `feat: add roam control panel` → `场景漫游控制面板开发`
   - `refactor: 接口字段适配` → `配合后台接口变更`
3. **保持简洁**：每条工作项一句话，不超过 30 字
4. **保留技术关键词**：UI、API、bug、URL 等技术术语保留不翻译
5. **按重要性排序**：主要功能开发排前面，bug 修复和优化排后面

### 步骤 7：补充非 git 工作

git 提交只能反映代码工作，还需要询问用户补充：

- 面试、会议、培训等非编码工作
- 技术调研、文档编写等不一定提交代码的工作
- 服务器运维、部署等操作类工作

这些归入"其他"分类，或按用户要求创建对应分类。

### 步骤 8：收集下周计划

git 提交无法反映下周计划，必须询问用户：

> 下周计划做什么？可以按项目简单说一下。

用户可能自己手写，也可能描述后让你整理。用户暂时没有计划时，下周计划部分写
"（暂无，待补充）"而不是留空或编造。

### 步骤 9：生成并确认

1. 按模板输出完整周报；项目名称直接用仓库名，monorepo 用子应用（scope）名
2. 请用户确认条目内容是否准确
3. 用户确认后定稿

## 示例

**示例 1：用户手动描述（无 git 仓库）**

> 这周主要在做项目A的地图模块，漫游功能基本完成了，还在做数据目录树。项目B门户 UI 在改。还面试了两个前端。

**生成输出：**

```
本周完成工作:
一、项目A
1. 场景漫游功能开发
2. 数据目录树功能开发中

二、项目B
1. 门户 UI 优化

三、其他
1. 前端面试

本周工作总结:
-

下周工作计划:
（请补充下周计划）
```

**示例 2：多仓库自动发现 + monorepo 拆分**

配置目录下扫描到 repo-a、repo-b、mono-repo 三个仓库本周有提交。
mono-repo 是 monorepo（存在 pnpm-workspace.yaml 和 apps/、packages/ 目录），本周提交为：

```
feat(app-a): 智能体创建高级设置默认上下文 Token 数改为 200000
refactor(services): 响应拦截器解耦 UI 并收敛各应用接入
chore: prettier 全局格式化并更新 .prettierignore 忽略规则
feat: 参数配置删除增加二次确认弹窗   ← 无 scope，git show 显示改的是 components
```

拆分结果：app-a、services、components 各成一组，"prettier 全局格式化"无法归属归入"工程化"。
项目名称直接用仓库名或 app 名，生成：

```
本周完成工作:
一、app-a（mono-repo）
1. 智能体创建高级设置默认上下文 Token 调至 200000

二、services（mono-repo）
1. 响应拦截器解耦 UI，统一各应用接入方式

三、components（mono-repo）
1. 参数配置删除增加二次确认弹窗

四、工程化（mono-repo）
1. 全仓 prettier 格式化并更新忽略规则
...
```

## 注意事项

- **不要编造**：只从 git 提交和用户描述中提取工作内容，不自行添加
- **项目名称用仓库名/app 名**：仓库名或 monorepo 子应用（scope）名直接作为周报项目名，不额外起业务名
- **自动发现不是终点**：扫描结果必须经过用户确认，用户补充的路径同样重要
- **本周工作总结**默认填 `-`（用户通常留空），除非用户明确提供总结
- **容错友好**：仓库路径不存在或无提交时，清晰标注而不是报错
- **先自动后手动**：优先用 git log 自动生成，再让用户补充非 git 工作和下周计划
- **提交信息是线索，不是定稿**：git commit message 需要翻译成业务可读的工作描述，不要原文照搬
- **monorepo 是常态**：遇到 apps/ + packages/ 结构的仓库，先按 scope/路径拆分再提取工作项
